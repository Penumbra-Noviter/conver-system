> 调研日期：2026-08-27。对象：`D:\Desktop\Craft` 下 13 个开发项目的任务池文档。方法：全文/抽样读取 + 结构 grep + 逐项目核对规则文本。结论：**应当改造，且可行**——问题单一（归档区缺出口），先例充分（TECH_DEBT 清出机制、DEV_LOG 滚动折叠）。

## 1. 问题：任务池文档只进不出，全部 13 份无一例外

## 2. 根因：不是「没写规则」，是「叙述职责错位」

### 2.1 通用根因：归档区缺出口

入口规则（每个项目都有）与 TECH_DEBT 的清出机制（2026-08-24 已固化）形成对照：

| | TECH_DEBT.md（有清出） | TO-TICKETS.md（无清出） |
|---|---|---|
| 候选/活跃区 | 只留开放条目 📝🔄 | 只留未完成工单 ✓ |
| 处置/归档入口 | 处置后整行移出候选区 ✓ | 完成后移入归档 ✓ |
| **出口** | **处置记录滚动保留最近 2 节，更早 git 承担** | **❌ 只进不出** |

TECH_DEBT 的经验证明「滚动保留最近 N 节 + git 历史兜底」在同样开发节奏下可用（13 份 TECH_DEBT 全部维持 2 日期节以内）。

### 2.2 conver system 特因：TICKETS 归档 = DEV_LOG 的逐字副本

抽查 F-90 / F-82~89 / S1~S3 / F-80~81 / F-74~79 五批：TICKETS.md 归档节与 DEV_LOG.md 同名节的「来源 / Grilling 共识 / 验证链 / 过程遥测 / 非阻断落债」**逐字相同、成对双写**。DEV_LOG 已有滚动机制（头部规则：窗口上限 12 条，超限折叠为阶段摘要回落 6~8 条），TICKETS 归档没有 → 同一份叙述被写两遍，只有一份会滚动。

其余项目的 TO-TICKETS 归档多为「表」（编号/标题/日期/提交）无叙述长文，膨胀程度低；conver 的高体积来自叙述双写 + 批次段 30~80 行/批。

## 3. 改造方案：为任务池文档补「归档出口」

与 TECH_DEBT 清出机制同构，低学习成本。规则草案（写入 AGENTS.md §3 任务清单生命周期为全局基准，各项目文档头部引用）：

### 规则 A：已完成归档滚动保留（防线性膨胀）

1. 归档区按批次分节（现状已如此），**完整保留最近 6 个批次**（或最近 2 周，取更宽者；参数可调，见 §5）
2. 更早批次折叠为「历史归档索引」**单行**：`批次名 | 日期 | 工单数 | 提交范围 | 一句话摘要`——保留工单号与提交哈希，防 review 重复提议、保工单号可引用
3. 索引行超过 60 行时，最旧的整段删除——归档由 git 历史承担（`git log -p -- TO-TICKETS.md`），与 TECH_DEBT 第 3 条同款
4. 清出动作绑定既有节点（每会话结束、commit 前，与 TECH_DEBT 清出同一动作），不新增仪式

### 规则 B：叙述职责归位，消除双写（conver system 及同类）

- 任务池文档归档区**只承载工单事实**（表：编号/标题/F 项/日期/提交）
- 叙述（来源/Grilling 共识/验证链/过程遥测/落债）**只写 DEV_LOG**（已有 12 条滚动机制），归档批次末尾一句引用：`详见 DEV_LOG「<节标题>」`
- 效果预估（conver）：批次段 30~80 行 → 5~8 行；897 行 → 约 150 行（60 批 × 6 行 + 索引）

### 规则 C：入口纪律补显式化（现有反例）

- 活跃表禁止 ✅ 滞留：会话结束 commit 前检查「活跃表无 ✅」为显式一步（Profit 9 行 ✅ 滞留、通用存档修改器 3 条 [x] 滞留已在本次调研中发现）

## 4. 推行策略（13 个项目全部可推行，风险受控）

1. **权威落点**：规则写入 `AGENTS.md` §3「任务清单生命周期」（全局唯一权威，所有项目 preflight 自动读取）；各项目 TO-TICKETS 头部引文块加两行摘要 + 指向（同 TECH_DEBT 的引用模式）
2. **试点先行**：conver system（最典型：最大膨胀 + 双写 + 规则模板原型）→ 验证规则可行性后，复制到 DDF / Profit（同模板复制项目，头部文字一次改动多点生效）
3. **分批落地**：重度文件（model-fingerprint 3730 行）单独会话执行一次「归档压缩」（44 批次段 → 索引 + 保留最近 6 批）；轻量项目（GameCheating 族 / 代订场 / 抖音 / Personal）仅补头部规则条款，无实际清出动作
4. **一次性压缩动作** = 全历史批次折叠为索引行（破坏性，但全部 13 项目均在 git 跟踪内，`git log -p` 可完整恢复；通用存档修改器已确认在 GameCheating 仓库跟踪内）

---

## 5. 待拍板参数

| 参数 | 建议值 | 备选 |
|------|--------|------|
| 完整保留窗口 | 最近 **6** 个批次 | 最近 2 个日期节（一天多批的项目会偏宽） |
| 索引滚动上限 | 60 行 | 50 / 100 |
| 叙述归位执行范围 | 全部项目（新批次起） | 仅 conver system（历史批次不再回改） |

## 6. 风险与边界

- **工单号可引用性**：折叠/删除后工单号（T-01、G1、F-xx）仍可能被评审引用 → 索引行保留工单号清单兜底；超窗口的靠 `git log` 找回
- **验收细节可查性**：双写消除后验收细节只在 DEV_LOG / git log，不在任务池文档——信息不丢，位置变更
- **不回改历史**：叙述归位只约束新批次，既有归档批次在首次压缩时一并折叠，不为历史做逐字搬家（省力的同时 git 历史保留原文）
- **非破坏边界**：活跃表永不滚动；Tag 表/B 类入口规则全部不动
