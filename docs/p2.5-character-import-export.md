# P2.5 SillyTavern V2 角色导入/导出 — SPEC

> 状态：✅ 已完成（2026-08-03）
> 范围：角色卡 **JSON 格式** 导入/导出 + 手动创建完整性引导
> 相关：CONSENSUS §3、TICKETS P2.5

---

## 1. 背景与目标

- 角色 ORM 已完整映射 SillyTavern Character Card V2 字段（见 `models/character.py` 头注释），但缺少 **导入/导出转换逻辑与 UI 入口**。
- 目标：用户能从 SillyTavern 生态导入角色卡（`.json`），也能把自己创建的角色导出为 ST 兼容卡分享出去。
- 附带目标：手动创建角色时，若设定不完整，**引导**用户补齐（软提示，不拦截）。

## 3. 角色卡 JSON 格式规范

### 3.1 导出格式（V2 信封）

```json
{
  "spec": "chara_card_v2",
  "spec_version": "2.0",
  "data": {
    "name": "角色名",
    "description": "简短描述",
    "personality": "人格设定",
    "scenario": "场景设定",
    "first_mes": "开场白",
    "mes_example": "对话范例",
    "system_prompt": "自定义系统提示（可空）",
    "post_history_instructions": "历史后指令（可空）",
    "alternate_greetings": ["备选开场白1"],
    "tags": ["冒险", "奇幻"],
    "creator": "创作者",
    "character_version": "1.0",
    "creator_notes": "创作者备注",
    "avatar": "<base64 或 null>",
    "extensions": {
      "conver_system": {
        "temperature": 0.7,
        "avatar_url": "https://...",
        "character_book": {}
      }
    }
  }
}
```

### 3.2 字段映射

| DB 字段 | V2 data 字段 | 备注 |
|---------|-------------|------|
| name | `name` | 必填 |
| description | `description` | |
| personality | `personality` | |
| scenario | `scenario` | |
| first_mes | `first_mes` | 同名 |
| mes_example | `mes_example` | |
| system_prompt | `system_prompt` | |
| post_history_instructions | `post_history_instructions` | |
| alternate_greetings | `alternate_greetings` | list |
| tags | `tags` | list |
| creator | `creator` | |
| **version** | **`character_version`** | ⚠️ 仅此字段名不同 |
| creator_notes | `creator_notes` | dict |
| extensions | `extensions` | 合并 `conver_system` 命名空间 |
| avatar | `avatar` | base64 data URI → 原始 base64；URL 头像 → `extensions.conver_system.avatar_url` |
| temperature | `extensions.conver_system.temperature` | 非标准字段，走命名空间 |
| — | `extensions.conver_system.character_book` | lorebook 原样保真，本版不消费 |

### 3.3 头像往返规则

- **导出**：DB `avatar` 为 base64 data URI → 写 `data.avatar`（去 `data:image/...;base64,` 前缀，存原始 base64，ST 兼容）；DB `avatar` 为 URL → 写 `extensions.conver_system.avatar_url`。
- **导入**：`data.avatar` 存在 → 存为 `data:image/png;base64,` + 原值（MIME 推断为 png，浏览器展示无碍，MVP 限制见 §6）；否则 `extensions.conver_system.avatar_url` 存在 → 存 URL；否则 `null`。

### 3.4 导入格式识别（from_v2_card 入口）

按优先级识别，返回归一化的 `CharacterCreate`：

1. `spec == "chara_card_v2"` → 取 `data` dict
2. `spec` 存在但不是 v2 → **422**「不支持的卡片规格」
3. 顶层含 `char_name` → **V1 旧卡**，字段归一化：
   | V1 | V2/DB |
   |----|-------|
   | char_name | name |
   | char_persona | personality |
   | char_greeting | first_mes |
   | example_dialogue | mes_example |
   | world_scenario | scenario |
   | creatorcomment | creator_notes |
   | char_version | version |
   | description | description |
4. 顶层含 `name`（无 spec/data 信封）→ **裸 data**，直接按 V2 data 字段读
5. 否则 → **422**「无法识别的角色卡格式」

## 4. 后端设计

### 4.1 转换层 — `services/character_card.py`（深模块）

```
__all__ = ["to_v2_card", "from_v2_card"]
```

- `to_v2_card(char: Character) -> dict`：ORM → V2 信封 dict。`extensions.conver_system` 命名空间：temperature / avatar_url / character_book（lorebook）/ 其它未知 extensions 原样透传。
- `from_v2_card(card: dict) -> CharacterCreate`：卡 dict → 可落库的 Pydantic 对象。内含 §3.4 格式识别 + V1 归一化 + 头像往返 + extensions 命名空间回读（temperature 优先取命名空间，无则默认 0.7；非 V2 标准 extensions 内容回写 `creator_notes.conver_system_extensions` 保真）。
- 异常：格式无法识别 → `ValueError`（路由层转 422），不抛 Pydantic 裸错误。

### 4.2 导出 API — `api/routes/characters.py`

```
GET /api/characters/{character_id}/export
```

- `service.get_character_with_count` 校验存在（404）。
- 响应：`JSONResponse(to_v2_card(char))`，`Content-Disposition: attachment; filename*=UTF-8''{name}.json`（文件名 URL 编码，防中文/特殊字符问题）。
- 复用 `service.to_v2_card`，路由不写业务逻辑。

### 4.3 导入 API — `api/routes/characters.py`

```
POST /api/characters/import
```

- 请求体：卡原始 JSON（任意 dict）。
- 流程：`from_v2_card(card)` 归一化 → `service.create_character(db, data)` 落库（直接新建，D3）。
- 响应：`201` + `CharacterResponse`。
- 错误：`ValueError` → 422「导入失败：<原因>」；缺 name → 422「角色名称不能为空」。
- **不校验完整性**（D6：导入路径不参与引导）。

## 5. 前端设计

### 5.1 导入 UI（角色视图头部）

- `#btn-import-character` 按钮（「＋ 创建角色」旁，样式 `btn-secondary`）：点击 → 隐藏 `<input type="file" accept=".json,application/json">`。
- 选择文件后 `FileReader.readAsText` → `JSON.parse` → `POST /api/characters/import`。
- 成功 → toast 成功 + `loadCharacters()` 刷新；失败 → toast 错误信息（解析失败/导入失败）。
- `JSON.parse` 失败 → 前端直接提示「不是有效的 JSON 文件」，不发请求。

### 5.2 导出 UI（角色卡片操作区）

- 卡片操作区（现 💬/✏️/🗑️）新增 📤 导出按钮。
- 点击 → `fetch GET /api/characters/{id}/export` → `blob` → `<a download="{name}.json">` 下载（复用 `downloadExport` 的 Blob 下载模式）。

### 5.3 手动创建完整性引导（D6）

- **完整标准**：`name` + `personality` + `first_mes` 三项均非空。
- 表单（`character-form.js`）：
  - 三个字段任一为空 → 该字段 label 旁标黄/红提示「建议填写」，`field-hint` 显示「完整角色建议包含：人格设定 + 开场白」。
  - 保存时若缺项 → 汇总提示「⚠️ 设定不完整：未填写 人格设定/开场白。建议补齐后保存，仍要保存吗？」→ 确认/继续 可保存（软提示，不拦截）。
- 仅 `character-form.js`（手动新建/编辑）生效；导入路径无此提示。

## 6. 边界与异常

| 场景 | 行为 |
|------|------|
| 卡缺 `name` | 422「角色名称不能为空」 |
| 卡 spec 非 v2/v1 | 422「不支持的卡片规格」 |
| 卡结构无法识别 | 422「无法识别的角色卡格式」 |
| 头像 base64 超大 | 假设上限 2MB，超限截断并记日志（MVP 不做严格校验） |
| 重名角色 | 直接新建，允许重名（D3） |
| 导出文件名含中文 | `filename*=UTF-8''` 编码 |

## 7. 验收标准

- [x] 导出一张角色 → 文件为合法 V2 信封 JSON，ST 可正常读取
- [x] 导入该文件 → 角色完整还原（含 temperature/URL 头像/lorebook），**往返不丢数据**
- [x] 导入 V1 旧卡（char_persona 等旧字段）→ 正常落库，字段正确映射
- [x] 导入裸 data JSON（无信封）→ 正常落库
- [x] 导入非法 JSON / 无法识别卡 → 422 友好报错，前端 toast 展示
- [x] 手动创建空人格/空开场白 → 出现软提示，仍可保存
- [x] 手动创建完整角色 → 无提示
- [x] 转换层单元测试：V2 往返、V1 归一化、裸 data、非法卡、头像三种形态
